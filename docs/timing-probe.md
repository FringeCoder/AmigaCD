# Timing cross-check against Copperline

Measuring the core's chipset timing in numbers rather than photographs, by
running the same probe disk on our core and on an independently written
emulator and diffing the two columns.

**Status: the emulator half works and its column is committed. The MiSTer half
has never been run.** It rests on one assumption nobody has tested — that the
core's serial output reaches a host device we can read over ssh — and
`scripts/timing-probe.sh diagnose` exists to settle that before anything else.

## Why this exists

`docs/core-accuracy-todo.md` in the core repository opens by saying we cannot
measure against real hardware. That is what leaves its beam-counter and
bus-timing items tagged `[SUITE]`: they need a MiSTer, a screen, and a person
reading values off it, which is why several have sat untouched since the
backlog was written.

[Copperline](https://github.com/CopperlineHQ/Copperline)'s `timing-test/`
directory holds 55 hand-written 68k probes that measure a fixed amount of CPU
and chip-bus work against the CIA-A E-clock. They display their results on
screen — deliberately inside the CRT-safe area, so they can be photographed on
real hardware — **and stream the same values out the serial port as ASCII hex**.
Our core has a UART. So the same disk runs on both and the comparison is a diff.

Copperline is not silicon either. Where the two columns disagree that is a
question, not a verdict: it says the two implementations time that operation
differently and one of them is wrong. What the harness removes is the manual
step, not the uncertainty.

## The procedure

### 1. Diagnose first

```sh
./scripts/timing-probe.sh diagnose
```

This asks the MiSTer what its UART actually looks like: which core is loaded,
which `uartmode` is set, which serial devices exist, and whether anything (a
getty especially) is already holding one. **Run it before anything else.**

MiSTer's userspace shells out to `uartmode N` (`user_io.cpp`, `SetUARTMode`) to
bridge the FPGA's UART to the board's physical port. What is attached to that
port afterwards is not something this repository can know in advance, and
guessing is how an afternoon gets spent debugging an empty capture.

The likely answer is `/dev/ttyS1`. If a getty holds it, stop that getty for the
duration rather than fighting it for bytes — the interleaving is silent and
looks exactly like a timing fault.

**Record what worked here when you find out.** That is the point of this
section; right now it is a question, and it should end up being an answer.

### 2. Get the disk onto the card

```sh
./scripts/timing-probe.sh adf /path/to/copperline
```

Builds `timing-test.adf` from Copperline's committed probe binaries and copies
it to the MiSTer. The ADF is 900 KB of generated artifact so it is not
committed; it is rebuilt from bytes that are. `TIMING_PROBE_REMOTE` overrides
where it lands.

This needs no m68k assembler. Copperline's own `build.sh` assembles the probes
with vasm first, but the `.bin` files are in its repository and `make_adf.py`
wraps them on its own.

### 3. Mount it, then compare

Mount the ADF in `df0` from the OSD, set a UART mode, reset the core, then:

```sh
./scripts/timing-probe.sh compare
```

It captures from the serial device for 40 seconds and prints our column beside
Copperline's, row by row, marking the ones that differ.
`TIMING_PROBE_DEV` and `TIMING_PROBE_SECS` override the device and the window.

## The reference column

`docs/reference/timing-probe-copperline.txt`, 32 rows, regenerated with:

```sh
./scripts/timing-probe.sh reference /path/to/copperline
```

That needs a release build of Copperline, which is not free: **rustc 1.95+**,
`libudev-dev` and `libasound2-dev` (all three were fatal when absent), and about
19 minutes. Prebuilt routes exist — Homebrew, AppImage, Flatpak, and a Windows
build. The committed column means `compare` never needs any of that.

The column is pinned to a Copperline revision, recorded in the file's header.
Regenerate it when that moves, in a commit that says which rows changed.

## What each row measures

`timing-test/README.md` in the Copperline repository, which also records which
rows already have a real-hardware column and which are emulator-only. Rows 4, 5,
7, 14 and 28-30 turn on the 68020's taken-branch cost; rows 16, 17 and 21 are
per-frame VHPOSR-polling loops that expose the extra colour clock a CPU
custom-register read costs over a chip-RAM read — the same class our beam
readback work is about.

## The other instrument

The core repository has a second Copperline-derived check that needs no
hardware at all: `rtl/sim/beamcounter/tb_beamcounter_reference.sv`, which
compares `agnus_beamcounter.v`'s VPOSR/VHPOSR against a table generated by
`tools/copperline-beamtable.sh` and runs in CI. That one is done and green.
This one is the half that needs the machine.
